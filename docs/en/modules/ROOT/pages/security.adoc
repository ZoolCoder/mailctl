= Security
:description: What mailctl guarantees about credentials, destructive changes and the admin page.

mailctl holds API tokens for DNS and mail providers. It can create, change and
delete real mailboxes. Its security properties are part of its behaviour, and
tests enforce the ones on this page.

To report a vulnerability, open a
https://github.com/zoolcoder/mailctl/security/advisories/new[private security advisory].
Do not open a public issue. If a credential of yours has been exposed, rotate it
first, and do not send it to us.

== Credentials

Nothing sensitive reaches stdout::
Not an API token, not an OAuth access token, not a mailbox credential. A token
on stdout ends up in a pipeline, a CI log or a terminal scrollback.

The config file holds no credential::
The config names an environment variable. mailctl reads the value from the
environment, or from the macOS Keychain, at the moment it needs it. An unset
variable is an error, never an empty string.

Secrets are redacted in diagnostics::
Each API client's `String()` omits its secret, so an error that includes a
client cannot leak it. A failing OAuth token request never echoes its response
body, because Microsoft's token endpoint reflects the request, client secret
included.

Generated credentials are reported once, and only when they exist::
A credential is reported when the mailbox exists at the provider, not when it
is planned. After a partial failure you get exactly the credentials that are
live. If writing them to a file fails, they go to stderr instead, because a
generated credential cannot be read back from any provider.

See xref:environment.adoc[Credentials and environment] for where each value is
read from and where generated ones go.

== Destructive changes

* Deleting a mailbox needs `-prune` *and* `-prune-mailboxes`, then a prompt
  that asks you to type the domain name. `-yes` skips only the prompt.
* Omitting `catchAll` means "leave whatever exists alone", never "delete it".
* A DNS record mailctl did not create is never overwritten silently. A conflict
  fails the plan until you pass `-replace-dns`.
* Users are addressed by provider object ID where the API allows it, never by
  an address that another account might also match.
* A flag scoped to one command is rejected on the others rather than ignored.

See xref:commands.adoc#on-pruning[On pruning].

== Agents

An agent that uses `mailctl mcp` cannot delete anything, cannot apply a plan
you did not see, and cannot read a credential. DNS records, provider replies
and imported configs are treated as data, never as instructions. See
xref:agents.adoc[Agents and MCP].

== The admin page

`mailctl ui` listens on loopback only and has no login. It refuses requests for
another host name and writes that another site starts, and it runs under a
strict Content-Security-Policy. It cannot apply changes. See
xref:ui.adoc#security[The admin page].

== Scoping your tokens

* Give the Cloudflare token DNS edit permission on only the zones mailctl
  manages, not the whole account.
* Use a dedicated Microsoft Entra app registration for mailctl. The application
  permissions it needs (`Domain.ReadWrite.All`, `User.ReadWrite.All` and
  `Organization.Read.All`) are broad, so do not reuse an app that has other
  grants.

== Scope

mailctl is a client. It does not receive, store or relay mail. Its only
listener is the loopback-only admin page, which runs only while `mailctl ui`
does. The MTA-STS policy Worker it can deploy to Cloudflare serves one static
policy document over HTTPS and reads no input.
