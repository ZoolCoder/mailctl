= mailctl
:description: Declarative email configuration for custom domains.

[.hero]
--
One YAML file describes the DNS records, mailboxes, aliases, routing and
deliverability policy for every domain you own.

mailctl reads live state from each provider, diffs it against that file, prints an
ordered plan, and applies exactly what it printed. A single Go binary with one
non-stdlib dependency — no daemon, no state file, no lock.
--

[.cta]
xref:quickstart.adoc[Get started] xref:install.adoc[Install] https://github.com/zoolcoder/mailctl[GitHub]

[source,console]
----
$ mailctl plan

example.com
-----------
  CREATE  dns         MX example.com -> mailserver.purelymail.com  [purelymail]
  CREATE  dns         TXT example.com -> v=spf1 include:_spf.purelymail.com ~all
  CREATE  dns         CNAME purelymail1._domainkey.example.com
  CREATE  domain      add example.com  [purelymail]
  CREATE  mailbox     create contact@example.com  [purelymail]

9 actions

Run `mailctl apply` to make these changes.
----

== What it manages

[.cards]
* *Domains* +
Registers a domain with a mail provider and completes its ownership verification.
* *DNS* +
Publishes MX, SPF, DKIM, DMARC, MTA-STS, TLS-RPT and BIMI records in Cloudflare,
and refuses to clobber records it does not recognise.
* *Mailboxes* +
Creates real mailboxes at the provider, generating a credential when you do not
supply one and reporting it exactly once.
* *Deliverability* +
Merges every provider's SPF requirement into the single TXT record RFC 7208
permits, and can deploy a Worker to serve an MTA-STS policy.

| xref:providers/cloudflare.adoc[Cloudflare Email Sending] | outbound | — | — | —

Microsoft 365 lacks aliases and catch-all not because mailctl declines to
implement them: Graph exposes `proxyAddresses` as read-only and offers no
catch-all surface. mailctl rejects those config blocks with an error naming the
admin centre rather than accepting them and doing nothing.

== Three ideas carry the whole tool

Desired state::
The YAML file is the only description of what should exist. Nothing is stored
elsewhere, so there is no drift between mailctl's idea of the world and the world.

Plan then apply::
`plan` reads live state, diffs it, and prints an ordered list of actions. It
changes nothing, and performs no I/O once planning has begun. `apply` executes
exactly that list. `mailctl ui` shows the same plan and audit in a browser
instead of a terminal — read-only in this release — and `plan -json` gives the
same action list as JSON for a script.

Idempotence::
Running `apply` twice is the same as running it once. A converged domain reports
`No changes.` — which is what makes the tool safe to run from a terminal at any
time.

== What it deliberately does not do

mailctl refuses to pretend. Where a provider's API cannot express something, the
config rejects it with an error naming the manual route rather than accepting the
setting and ignoring it. An ignored setting reads as a setting that is in force,
which is worse than an error — an ignored `requireTwoFactorAuthentication` looks
exactly like enforced two-factor authentication.

Anything that can lose mail is deliberately awkward: deleting a mailbox needs
`-prune` *and* `-prune-mailboxes`, then a confirmation that asks you to type the
domain name.
