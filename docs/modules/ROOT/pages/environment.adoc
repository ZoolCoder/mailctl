= Credentials and environment

mailctl treats credentials as the most dangerous thing it handles. Two rules shape
the design:

. **Nothing sensitive is ever written to stdout.** Not an API token, not an access
token, not a mailbox password. Generated mailbox credentials go to stderr or to a
file with mode `0600`, and nowhere else. A password on stdout ends up in a
pipeline, a log, or a terminal scrollback.
. **Nothing sensitive is stored in the config file.** The config names an
*environment variable*; mailctl reads the value from the environment at the moment
it is needed.

== Environment variables

[cols="2,1,3"]
|===
| Variable | Required | Purpose

| `CLOUDFLARE_API_TOKEN` | always | DNS edit permission on the zones you manage. Also used for Email Routing, Email Sending and Worker deployment where configured.
| `CLOUDFLARE_ACCOUNT_ID` | usually | Referenced from the config as `+${CLOUDFLARE_ACCOUNT_ID}+`. Needed by the account-scoped Cloudflare APIs.
| `PURELYMAIL_API_TOKEN` | purelymail domains | Purelymail API access.
| `MS365_TENANT_ID` | ms365 domains | The Microsoft Entra tenant id.
| `MS365_CLIENT_ID` | ms365 domains | The registered application's client id.
| `MS365_CLIENT_SECRET` | ms365 domains | The application's client secret.
|===

A variable referenced by the config but unset is an error, never an empty string.
Substituting nothing silently would publish a broken record or create a mailbox
with an empty password.

== Scoping the Cloudflare token

Give the token DNS edit permission on the specific zones mailctl manages, not on
every zone in the account. An account-wide DNS-write token is convenient during
setup and a liability afterwards.

== Mailbox credentials

A mailbox entry may name an environment variable:

[source,yaml]
----
mailboxes:
  - address: contact@example.com
    passwordEnv: CONTACT_PASSWORD
----

Or omit it, in which case mailctl generates one:

[source,yaml]
----
mailboxes:
  - address: contact@example.com
----

A generated value is 24 characters from a cryptographic random source, roughly 150
bits of entropy. It is produced only when mailctl actually has to create that
mailbox — an existing mailbox is never given a new one by accident.

=== Reported exactly once

A generated value is reported when the mailbox is genuinely created at the
provider, not when it is planned. That distinction is load-bearing: reporting at
plan time would hand you passwords for mailboxes a later failure meant were never
created, with no way to tell which were real.

[source,console]
----
$ mailctl apply -secrets-out new-mailboxes.txt
...
Wrote 1 generated credential(s) to new-mailboxes.txt
----

If a run fails partway, only the values for mailboxes that were actually created
are reported. That count is the one you can rely on.

=== The output file

It is created with mode `0600` using an exclusive create, so an existing path is
refused rather than overwritten. If writing fails for any reason, the values are
reported on stderr instead — losing a live credential silently is not an
acceptable failure mode.

=== After a handover

Retrieve the values, store them in a password manager, delete the file. Where the
provider supports it, mailctl marks a generated password as one that must be
changed at first sign-in, so the recipient ends up with something nobody else has
seen.

== Keeping the file out of git

Add the ignore rule before creating the file, not after:

[source,console]
----
$ printf '*.secrets\n' >> .gitignore
----

mailctl never reads a credential from the config file, so the config itself is safe
to commit — but check it for real addresses before publishing it anywhere.
